# tape-base58

[![Crates.io](https://img.shields.io/crates/v/tape-base58.svg)](https://crates.io/crates/tape-base58)
[![Documentation](https://docs.rs/tape-base58/badge.svg)](https://docs.rs/tape-base58)
[![License](https://img.shields.io/crates/l/tape-base58.svg)](LICENSE)

A fast base58 implementation for Rust, built for Solana's public keys and
signatures. It's `no_std`, never allocates, and has no dependencies.

## Why it's fast

58 isn't a power of two, so base58 can't split input into bit groups the way
base64 does. The textbook method, which `bs58` uses, treats the input as one
big number and divides all of it by 58 for every character it writes.

Most Solana data is a 32-byte key or a 64-byte signature, and at a known size
that work can be precomputed. Following Firedancer, each 32-bit word of input
is multiplied by a fixed table of its value in base 58^5. The sum is a set of
limbs holding five digits each, which only need carrying and splitting. There's
no long division. The vector code then carries every limb at once instead of
one after another:

| target | encode | decode |
|---|---|---|
| aarch64 | the alphabet through one four-register table lookup | characters through the same lookup, inverted |
| x86-64 with AVX-512 VBMI | keys and signatures entirely in registers | the AVX2 kernels, which were never slower |
| x86-64 with AVX2 | keys and signatures entirely in registers, the alphabet as a compare chain | characters through a per-window shuffle |
| anything else | portable | portable |

The path is picked at runtime by asking the processor, because Agave builds
with `x86-64-v2`, which has no AVX2, so a crate that picks SIMD at compile time
runs scalar in a validator. The routing comes from measurements: Zen 4 runs
AVX-512 in two halves, so it gets the AVX2 key encoder, which is 15% faster
there.

On x86 under Agave's flags, that's 2 to 5x faster than `five8`. On chain there
are no vectors, and the portable code still uses 40 to 50% fewer compute units
than `five8`, which the Solana SDK uses to print addresses: 744 CU per
`msg!("{}", pubkey)` instead of 1,231. [BENCHMARKS.md](BENCHMARKS.md) has the
numbers, how to reproduce them, and four ways a benchmark of this crate can
mislead you.

## Using it

```toml
[dependencies]
tape-base58 = "0.1"
```

```rust
// Fixed widths, no allocation.
encode_32(&[u8; 32], &mut [u8; MAX_ENCODED_32]) -> usize
encode_64(&[u8; 64], &mut [u8; MAX_ENCODED_64]) -> usize
decode_32(&[u8], &mut [u8; 32]) -> Result<(), DecodeError>
decode_64(&[u8], &mut [u8; 64]) -> Result<(), DecodeError>

// Any length up to MAX_VARIABLE_LEN, which is one Solana packet.
encode(&[u8], &mut [u8]) -> Result<usize, EncodeError>
decode(&[u8], &mut [u8]) -> Result<usize, DecodeError>
encoded_len(usize) -> usize
decoded_len(usize) -> usize

// Four inputs at a time, sharing one walk of the table.
encode_32_batch(&[[u8; 32]], &mut [u8], &mut [usize]) -> Result<(), EncodeError>
encode_64_batch(&[[u8; 64]], &mut [u8], &mut [usize]) -> Result<(), EncodeError>
decode_32_batch(&[&[u8]], &mut [[u8; 32]]) -> Result<(), BatchError>
decode_64_batch(&[&[u8]], &mut [[u8; 64]]) -> Result<(), BatchError>
```

## The `variable` feature

`encode` and `decode` work at any length without it, but they walk the value
down one limb at a time. The `variable` feature adds about 400 KiB of
place-value tables, which makes a 1232-byte transaction about 6x faster to
encode and 4x faster to decode on Zen 5. Leave it out of on-chain programs.
Its decode overflows the 4 KB SBF stack frame, and the tables would cost rent.
